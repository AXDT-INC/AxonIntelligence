# Isolated supervised CPU integration candidate

Ready for independent integration audit, not production conversion. All conversion/verification entry points used by the candidate are restricted to synthetic fixtures under `test-workspace/`. Conversion rejects source manifest payloads above 17 MiB (16 MiB tensor budget plus metadata allowance). No production model payload has been read. Accepted V3 and the original optimization prototype are not replaced.

## Architecture and lifecycle

`convert_fp16.py`, `verify_fp16.py` and `audit_io.py` are isolated copies. `audit_io.py` is byte-identical to V3. Publication and CLI state handling remain Python operations: descriptor-relative reads, manifests, receipt isolation, exclusive staging, write loops, fsync, renameat2(RENAME_NOREPLACE), uncertain promotion outcomes, and cleanup/reporting fallback. Numerical reference routines are retained unchanged under explicitly named reference entry points. The reference path remains selectable; there is no automatic fallback.

`candidate.convert(..., selection='native'|'reference')` and `candidate.verify(...)` are the supported synthetic APIs. They establish a context-local engine. Native conversion splits V3 128 KiB buffers into ordered 64 KiB requests. Each carries cumulative statistics so ordered binary64 sums are preserved across splits. Python commits its caller's statistics only after the whole request succeeds. No native filesystem operations implement conversion or publication.

The internal verifier reopens every output shard and checks every tensor using the separately reviewed midpoint-interval verifier. Hashes do not substitute for numerical checks. A separate verification call launches a new worker. Both algorithms live in the same authenticated executable but never call each other's rounding routines. Same-toolchain/hardware assumptions remain shared. A compromised binary or coordinator is outside the trusted-operator model.

Before promotion, the coordinator requires a valid shutdown acknowledgement and successful worker exit. Any native rejection, malformed response, EOF, signal, timeout or failed shutdown prevents promotion. The subprocess is killed/reaped on errors and is never reused or silently retried. Startup failures are wrapped in preflight LifecycleError state. The native worker is already gone at promotion, so later receipt/directory cleanup cannot retroactively invalidate its completion. Cleanup now retains explicit ownership and cumulative diagnostics until reaping and resource closure are confirmed; unresolved cleanup is included in machine-readable lifecycle reports. See the V2 document for state transitions and limits.

## Protocol and resource limits

Linux x86-64 little-endian ABI version 1. Headers are six little-endian uint32 fields: magic 0x41584e31, version, sequence, operation/status, payload length, statistics length (80). Requests use operations 1 convert, 2 verify, 3 shutdown. Data requests carry 7 uint64 counters and 3 binary64 statistics followed by BF16 bytes and, for verification, FP16 bytes. Successful conversion replies carry statistics and output; verification carries statistics only. Shutdown has no statistics body. A fixed startup greeting confirms sandbox entry. Sequence, version, length, status and statistics plausibility are checked. Requests and responses are bounded; no unbounded stderr capture exists.

The default request timeout is 5 seconds (configurable at construction up to 30). IPC uses nonblocking pipes with deadline-controlled select/read/write loops. The worker has 128 MiB address-space and 120 CPU-second hard limits and disables core dumps. These limits intentionally suit synthetic candidate work, not full-model conversion. One worker/thread is supported per engine context; sharing a worker between concurrent threads is unsupported. Tests/benchmark pin to one logical CPU and nice 19. Nice is not a quota; active work can consume one core.

After startup, seccomp allows only reads from stdin, writes to stdout/stderr, exit and signal return. File opens, networking and other syscalls kill the worker. The filter is installed before the greeting. Dynamic loader/system libraries run before the filter and remain trusted. The coordinator is not OS-sandboxed; its copied filesystem policy and trusted operator remain essential. Synthetic-only paths and data limits must not be removed without separate review.

## Executable authentication and build

`build.py` uses fixed argument arrays, absolute `/usr/bin/gcc`, a small controlled environment and no shell. It compiles twice in fresh private candidate-local temporary storage and requires byte-identical executables. Exclusive no-follow creation prevents replacement of an existing worker. `trust.json` records ABI, numerical/worker source hashes, compiler identity/hash, flags, executable hash and repeat-build result. `CANDIDATE_MANIFEST.json` covers Python helpers, build source, tests and all other evidence.

The supervisor traverses directories with descriptor-relative/no-follow checks matching V3's policy, now with an explicit ownership ledger for authentication descriptors. Source, manifest and executable reads require unique regular files, current-user ownership and no group/world write bits. It hashes bounded executable bytes, copies those exact bytes to a memfd, seals against write/growth/shrink, and launches `/proc/self/fd/N` with that descriptor explicitly inherited. Path replacement after authentication cannot substitute the launched bytes. The authenticated trust-manifest hash is cached when recording conversion provenance. Independent artifact verification checks recorded engine/ABI/executable/manifest identity against the current reviewed trust manifest, including when the reference numerical engine verifies native-produced output. Tests actually launch the sealed executable after replacing the original pathname.

Trust is anchored in operator review of this directory and the candidate manifest; a writable trust manifest is not a cryptographic root against the same owner. Ancestors must remain trusted against hostile renames. System loader/libc/libm are not bundled or cryptographically pinned. Repeated local builds are verified; cross-machine builds are not claimed reproducible. GCC/source changes require a new reviewed build/manifest. No compilation occurs implicitly during conversion.

Rebuild only in a separately reviewed fresh candidate copy, or archive generated artifacts inside this workspace first: `PYTHONDONTWRITEBYTECODE=1 python3 -B build.py`. The builder refuses existing outputs. Test the current lifecycle revision with `PYTHONDONTWRITEBYTECODE=1 nice -n 19 python3 -B run_tests_lifecycle_v2.py`; reports use exclusive creation. Benchmark similarly with `benchmark_candidate.py`. Never delete previous evidence merely to rerun; use versioned names inside this directory. No Docker, install, network or GPU dependency is involved.

## Measured performance and limitations

See `benchmark-results.json` and `RESULTS.md`. Three 2 MiB trials per engine use identical synthetic safetensors. End-to-end conversion includes source hashing, file/header creation, internal numerical verification, output hashes, fsync, synthetic promotion and worker startup/shutdown. Independent verification reopens and validates the fixture separately. External receipt publication and failure recovery are excluded. Model distribution, cold disk, large shards and sustained contention are not measured.

Raw native kernel CPU timings are compared with supervised block wall times on identical payloads; their difference includes Python copies/validation, IPC and scheduling, not isolated transport time. Combined RSS is a conservative sum of separately observed parent/worker high-water marks, not a simultaneous sampled peak; fixture generation dominates the parent footprint. Three short trials do not establish confidence intervals or a production SLA. Linear extrapolation also repeats per-artifact fixed costs (startup and metadata operations) much more often than a large real shard would; conversely, cached tiny fixtures omit real storage pressure. The estimate can err in either direction.
