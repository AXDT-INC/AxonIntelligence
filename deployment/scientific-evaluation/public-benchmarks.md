# AxonAI-v1 public benchmark plan

**Proposed on 27 November 2026.** Compare the released FP16 AxonAI-v1 with its original Qwen checkpoint on the same two V100s. Run two hosted frontier models on the same questions to measure the remaining capability gap. The primary question is whether the release answers biomedical research questions more accurately than Qwen when both receive the article evidence. The proposed four-benchmark suite contains 6,200 items and schedules 24,800 answers. The central compute estimate is **33 hours on one GPU pair and $250 total**, before tax and staff time. This is a prospective plan. It contains no benchmark results.

## Reproduction and execution sequence

1. **Freeze inputs.** In private custody, record each source revision above, file SHA-256, schema, row count and ordered ID digest. Use PMID or the official ID where available, otherwise the zero-based row index in the pinned split, namespaced by suite. Resolve duplicate IDs and label indexing on independent fixtures. Verify license, attribution and permitted provider processing/retention per suite. Send providers only the question packet under approved account settings. Keep keys, training data, restricted examples and raw outputs outside Git. Record any provider-ineligible suite as unavailable and recompute the common denominator.
2. **Freeze the prompt and answer contract.** Use the system message `You are a scientific research assistant. Follow the requested answer format.` Render UTF-8 with LF line endings. Use `Question:` and the published stem, preceded by `Context:` and newline-joined passages on PubMedQA, followed by one option per line (`A. …` through `D. …`) on MCQ suites. End each request with `End with exactly one line: FINAL <answer>.` Replace `<answer>` in the instruction with the allowed labels or “a number”. Request only the final line for PubMedQA and MedMCQA. Permit brief working before it for GPQA and GSM8K. Freeze and hash the exact renderer and fixtures. Parse one final anchored `FINAL` line, trim surrounding whitespace, case-fold labels and reject conflicting final lines or trailing prose. Score the visible response only. Keep scorer and gold keys inaccessible to inference workers.
3. **Match local execution.** In a dedicated Docker Compose project, run a single resident model at a time on the same exclusive pair. Pin the image digest, code commit, driver, CUDA, PyTorch, Transformers, tokenizer, kernel settings, ordered GPU UUIDs and layer map. Freeze local batch size 1, greedy decoding, seed 42, thinking disabled, template generation prompt, EOS IDs and a fresh cache per item. Verify identical rendered token IDs locally. Limit input to 2,048 rendered Qwen tokens and output to 256 new tokens. Check fit on all items before dispatch. Record overlength cases across all arms and report full-frame coverage. Keep complete questions and options intact.
4. **Fix API conditions.** Send the same visible system/user text and option order in native API envelopes. Set a 4,096-token total generation allowance per hosted request to accommodate billed reasoning. Report each model's actual billed input/output, thinking usage where available, finish reason, and cap-hit rate. The hosted contrasts measure performance under these stated budgets. Equal visible prompts do not imply equal inference compute. Exact hosted responses can vary on replay. Compare published leaderboard figures only when their shot count, reasoning budget, sampling, tool access and scorer match.
5. **Qualify on disjoint fixtures after execution is authorized.** Compose tests should exercise label permutations, all three evidence labels, numeric normalization, malformed and capped answers, provider refusals, key isolation and interrupted/resumed runs. Then verify a synthetic full-length prefill/decode on each local arm, finite logits, device exclusivity, identical input IDs and repeatable greedy answers. Use disjoint development or synthetic items of representative lengths for provider compatibility, API usage and throughput. Revise and freeze the estimate before releasing any benchmark prompt. Check the common model profile on a private worker; the live production socket has a fixed identity prompt.
6. **Collect once and retain failures.** Interleave suites in seeded order and counterbalance local block order, half Qwen-first and half AxonAI-first. Keep a signed mapping of item, arm, block and request digest. Persist a claim before dispatch and resume only untouched slots. Allow at most two backoff retries for explicit pre-generation rate-limit rejections. Log every attempt and billed token. Treat ambiguous timeouts as missing, preserve returned refusals/invalid answers, and never reroll a completed answer. Freeze benchmark adapters, provider API settings, model versions and analysis before unblinding. Halt on identity drift, data exposure, device loss or an overspend forecast.
7. **Report paired results.** For each benchmark show scheduled, eligible, returned, parsed and correct counts. Report correct/eligible as operational accuracy, with a separate count for each infrastructure failure. For each paired contrast report wins, losses, both ties and percentage-point difference on jointly returned pairs, treating invalid answers and refusals as incorrect. Give best/worst bounds for missing outcomes over the eligible roster. Use a paired 95% bootstrap interval (10,000 resamples, seed 42), resampling source families together where linked. Use an exact two-sided McNemar test for the one primary AxonAI–Qwen contrast on PubMedQA if pairs are independent. Use a family-level paired permutation test if items share sources. Treat the three other suites and comparisons to the two APIs as descriptive. Show latency p50/p95, cap hits, tokens, peak device memory and dollars per 1,000 questions separately. Release aggregates, frozen settings, hashes, environment and scorer version so an authorized reviewer can reproduce scores from retained responses.
