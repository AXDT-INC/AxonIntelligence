# L40S worker integration · review before hardware execution

This implementation targets the accepted 80-pair diagnostic design. Only CPU mocks have exercised it. The hardware acceptance run uses disposable geometric/text controls. The accepted scientific endpoint, blinding scheme, 4,096-token context and 384-token output allowance remain as specified in the inference protocol.

## Components and trust boundary

The trusted supervisor runs on the reserved L40S host. It verifies a separately approved SHA-256 of a private plan and the allowlisted program package at startup. It starts one fresh container per block via the local Docker socket, using an immutable local image ID. Docker sends only a read-only code bundle, verified base mount and, for the adapted role, a separate verified adapter mount. The container has no network, credentials, host sockets, receipt database, private registry, answers or role mappings between slots. Its stdin accepts a strict typed session followed by jobs containing an opaque item ID, rendered digest, input token IDs and optional ordered continuation IDs. Keep the privileged host supervisor, host-admin access, image configuration, artifact mounts and identity logs outside inference orchestration. The scheduler receives opaque progress. The trusted provisioner and each model process necessarily know the local loading role.

The host must supply a vetted, secrets-free image without additional image-declared volumes, baked-in evaluation files, telemetry, startup customization or ambient credentials. Use read-only immutable package and model source snapshots accessible to container UID 65534. The host operator controls Docker, the reservation and approval pins; Docker access or write access to any pinned input effectively delegates that role. Check actual denied reads/listing and network egress with the custody protocol's benign canaries inside the deployment boundary. Store private files on encrypted local storage with controlled backup, retention and access logging.

The supervisor's SQLite ledger uses synchronous FULL transactions under a single-writer directory lock. Event HMAC-SHA256 binds session (plan and package digests), event name and exact payload. It commits the claim before dispatch and publishes a terminal result once. Reopening an intact completed ledger verifies bindings and skips execution. An interrupted claim becomes a terminal worker-loss record and halts the block. Explicit timeout, OOM, nonfinite outputs, malformed replies, runtime drift and worker crashes stop release. Untouched assignments remain on the frozen roster as unattempted. An invalidated freeze requires private incident disposition. Preserve it and use a newly authorized linked run for any repeat.

Use an independently provisioned random 32-byte secret in an owner-only file outside the package, model mounts and repository. The supervisor and authorized custody verifier hold the symmetric key. HMAC authenticates contents to key holders; private host ACLs and encrypted storage provide confidentiality. Keep an independently witnessed copy/digest of the closed ledger and its externally signed assignment roster to detect rollback, deletion or whole-store substitution. The code does not provide distributed key management or host compromise resistance. Use one authoritative ledger directory per (run, slot) and one key domain per approved run. Do not clone live databases, reuse a slot in a different directory, or place SQLite/locks on network filesystems.

## CPU acceptance

On clu1, the 40 committed protocol tests and 19 additional CPU-only integration tests passed. The new tests exercise the actual greedy cache loop, teacher-forcing alignment, numerical controls, frozen input/role checks, a complete simulated discovery/prepare/five-load/audit cycle, transactional receipt recovery, HMAC tampering, deadline enforcement, mount policy and reproducible packaging. The test backend uses mocks in place of CUDA, Torch, Transformers, PEFT and the Docker daemon. These results leave the model loader, NVIDIA isolation, numeric equivalence, memory ceiling and performance to be measured on L40S.

## Preparing the transfer

From clu1's repository root, with an output path that does not exist:

```sh
python3 -B deployment/scientific-evaluation/v1/live_package.py build /tmp/ax-l40s-worker.tar
sha256sum /tmp/ax-l40s-worker.tar
```

The deterministic tar has flat regular-file members: runner, backend, worker, supervisor, ledger, package verifier, the pinned packaging provenance, this runbook and SHA256SUMS. It carries neither model weights nor private records. Record the archive and inner manifest digests independently at approval. Transfer that archive through authorized aviX staging to the L40S host. Verify the out-of-band archive digest on each hop **before extraction**. Extract on L40S into a new empty dedicated directory; make it readable to the container user and immutable to runtime processes. Run the following there; the verifier checks all members and rejects extras, missing files and symlinks. Always invoke Python with `-B` to avoid writing bytecode to the package directory.

```sh
python3 -B live_package.py verify . "$PACKAGE_PIN"
```

## Runtime prerequisites and freeze

- Reserve the same two exclusive 48 GB L40S GPUs in fixed UUID order. Require SM 8.9, BF16 support, at least 38 GiB free per GPU before load, no other compute processes, and unchanged driver, clock/power and thermal policy. Confirm the host and container agree on GPU UUIDs, free memory and ECC state. CUDA UUID rendering and NVML compute-process visibility must be checked on the real host.
- Use the historical L40S baseline as the initial candidate: Linux, Python 3.12.3, Torch 2.13.0+cu132, CUDA 13.2, Transformers 5.16.1, PEFT 0.20.0, Accelerate 1.14.0, tokenizers 0.23.2, safetensors 0.8.0, numpy 2.5.2, huggingface-hub 1.30.0. Pre-existing compatible packages must already be present in the approved image. The CPU host supervisor requires Python 3.10+, Linux flock, local Docker CLI/daemon, and an approved local image SHA-256 ID. The image needs GNU timeout, python3 and the NVIDIA utility/compute runtime. Validate recursive read-only bind support (Docker and host kernel), memory/PID limits, local socket access and the NVIDIA runtime. The supervisor verifies the effective container configuration and bind inventory before starting the worker. [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)
- Stage clean flat read-only model directories exactly matching the provenance inventory. The bare role gets just the 18-shard pinned base, tokenizer, template, configuration and associated files. The adapter role additionally gets the original final weights and adapter config. A merged release cannot satisfy these pins. Reserve roughly 52.2 GiB of read-only artifacts in addition to the image. Use at least 128 GiB host memory plus OS headroom; the container limit is 128 GiB. Check local storage, GPU memory, cgroup enforcement and snapshot immutability before allocation.
- The 64 text layers use an explicit contiguous 32/32 split. The worker hashes the resident BF16 base parameter bytes and placement after any adapter attachment, including both endpoints, records discarded vision keys, and rejects missing or mismatched weights. It compares 992 loaded adapter tensors to the pinned file and verifies active, unmerged LoRA layers and their co-placement. Check the actual installed loader's return format, expected discarded vision keys, device-map coverage, BF16 parameter policy and PEFT active-layer APIs during discovery. The package assumes the validated text-only class and parameter count.
- Pin the software image including native extensions. Discovery records concrete package versions, CUDA build, optional backend inventory, driver and UUIDs, tokenizer and template bindings, kernel profile and base-state digest. The supervisor enforces the approved image by ID with local-only startup. The worker compares the observed common runtime to the locked discovery freeze before any scoring/generation. Verify review of the actual discovery preimages against independent operator records. Optional fast kernels, SDPA math availability and deterministic recurrent-layer operations depend on the installed builds.
- Text is rendered once through the verified base tokenizer using the accepted runner. Ordinary pilot workers receive those frozen IDs directly. Batch size one, no padding, no truncation, full causal prefix, default sequential positions, seed 42, BF16 autocast, math SDPA and deterministic algorithms apply to both arms. Decode takes greedy argmax on finite raw logits, reusing the causal cache. It stops at the first configured EOS or the common cap. A neutral warm-up probes the actual LoRA branch and BF16 result dtype. Check cached versus full-prefix semantics and reproducibility on synthetic controls before pilot authorization.

## Restricted operator procedure for a future hardware preflight

Use a private working directory outside Git (0700), 0600 plan/key files and umask 077. A model/rights reviewer and custodian approve the immutable package, model inventories, software image ID, enrolled hardware and preflight budget. No job in this procedure takes a real scientific question. The examples use previously provisioned operator variables. Run only after hardware approval.

1. Prepare an empty private `DISCOVERY` directory and a private `BLOCKS` parent. Initialize the discovery plan with the approved image ID (64 hex characters, without the sha256 prefix) and two ordered GPU UUIDs. Keep all generated plans/receipts private. Verify and register each printed plan digest through an authenticated out-of-band channel before passing it to a run.
2. Run discovery with the bare mount only. It verifies every base file, loads the text model, observes hardware/runtime state and renders the disposable controls without a forward pass. Review the authenticated ready event in private custody (see ledger access below), including the exact loader key inventory, runtime, memory and source/implementation bindings. A discovery observation becomes a freeze only after independent approval.
3. Prepare five separate fresh-load plans using the approved discovery record. They share the common runtime and identical two rendered fixtures: a short control and a full-envelope 3,712-input-token control. The latter uses repeated neutral padding in its user text. An unexpected tokenization length fails closed. Each fixture also carries two public continuation token sequences, including a multigram. The five distinct tickets cover bare, adapter-loaded-but-disabled, active adapter, a second bare and a second active load.
4. Run the five plans sequentially on the same two GPUs. Pass the adapter mount only for disabled and active loads. For each block inspect verified identity and warm-up, generation, teacher-forced continuation scores and a separate first-step full-vocabulary logit digest. The disabled arm loads the full adapter into a fresh model and wraps every forward in PEFT's disable context. The two bare processes each load from the untouched base. The active forward must exercise a BF16 LoRA branch. Confirm the preflight output lengths and both memory peaks. Independently of EOS, the full-envelope probe appends 384 forced neutral tokens through the causal cache, checks finite logits at every step and hashes the terminal vocabulary vector at token 4,096. For the short probe, require the cached next step to agree in top-1 with a full-prefix reference and have maximum absolute logit difference ≤0.5. This BF16 tolerance is a proposed hardware gate. Record the measured discrepancy before approving a pilot.
5. Run the synthetic audit on all five authenticated ledgers. It validates both tickets for each pair through the committed runner. It requires byte-identical rendered/device inputs, identical full-logit digests, greedy outputs and option likelihoods for bare versus disabled and for fresh-load repeats of each active role. At least one active-adapter probe must differ numerically from the bare control. Precommit this strict equivalence rule; if it fails, halt and examine the actual loader, adapter and deterministic-kernel behavior privately. The controls measure integration properties only.

```sh
python3 -B live_supervisor.py init "$DISCOVERY" "$IMAGE_ID" "$GPU0" "$GPU1"
python3 -B live_supervisor.py run --package-pin "$PACKAGE_PIN" --root "$DISCOVERY" --pin "$DISCOVERY_PIN" --key "$KEYFILE" --base "$BASE"
python3 -B live_supervisor.py prepare --package-pin "$PACKAGE_PIN" --root "$DISCOVERY" --pin "$DISCOVERY_PIN" --key "$KEYFILE" --output "$BLOCKS"
python3 -B live_supervisor.py run --package-pin "$PACKAGE_PIN" --root "$BLOCKS/bare1" --pin "$BARE1_PIN" --key "$KEYFILE" --base "$BASE"
python3 -B live_supervisor.py run --package-pin "$PACKAGE_PIN" --root "$BLOCKS/disabled" --pin "$DISABLED_PIN" --key "$KEYFILE" --base "$BASE" --adapter "$ADAPTER"
python3 -B live_supervisor.py run --package-pin "$PACKAGE_PIN" --root "$BLOCKS/active1" --pin "$ACTIVE1_PIN" --key "$KEYFILE" --base "$BASE" --adapter "$ADAPTER"
python3 -B live_supervisor.py run --package-pin "$PACKAGE_PIN" --root "$BLOCKS/bare2" --pin "$BARE2_PIN" --key "$KEYFILE" --base "$BASE"
python3 -B live_supervisor.py run --package-pin "$PACKAGE_PIN" --root "$BLOCKS/active2" --pin "$ACTIVE2_PIN" --key "$KEYFILE" --base "$BASE" --adapter "$ADAPTER"
python3 -B live_supervisor.py audit --synthetic --package-pin "$PACKAGE_PIN" --key "$KEYFILE" --block "$BLOCKS/bare1" "$BARE1_PIN" --block "$BLOCKS/disabled" "$DISABLED_PIN" --block "$BLOCKS/active1" "$ACTIVE1_PIN" --block "$BLOCKS/bare2" "$BARE2_PIN" --block "$BLOCKS/active2" "$ACTIVE2_PIN"
```

In the private operator process, `opened(root, approved_plan_pin, keyfile, package_pin)` authenticates the plan and ledger. Use `db.get("ready")`, `db.get("halt")`, and `collect(plan, db)` to read and verify restricted metadata. Restrict operator console and audit output. On interruption re-enter the same pinned run and ledger. The supervisor checks for a stale specifically labelled container and removes only that worker. A read timeout kills the isolated worker, signs the terminal status and halts. A completed slot is never silently regenerated. If a host supervisor is lost, the worker has independent load, idle and item alarms and an outer 4-hour lifetime ceiling. An operator must verify GPU context release after hard termination.

## Measures, budgets and abort conditions

For each delivered generation, retain exact suffix IDs, termination reason, token count including EOS, synchronized prefill-through-last-token wall seconds, time to first selected token, overall tokens/s, decode-only tokens/s when defined, per-GPU allocated/reserved peaks and process peak RSS. Option likelihoods are separate teacher-forced sums of FP32 log-softmax at the exact continuation token positions, in public option order. Provide only visible candidate alternatives, with continuation tokenization frozen against the exact rendered prefix and tokenizer; document spacing and whether EOS is part of the declared continuation. No implicit EOS, normalization, accepted option ID or answer key is supplied. Option timing is independent of generation timing. Optional likelihoods require prespecification before a real run; they do not override the locked scientific scoring rule. Infrastructure failures retain null output fields. Authenticated timing/digests and raw outputs remain private.

Plan **two exclusive L40S for up to two hours (four GPU-hours)** including review of cold-load observations within the reservation. Six loads re-verify about 0.33 TB of source bytes cumulatively plus roughly 0.32 TB of host transfers for base-value verification. Ten fixture generations produce at most 3,840 tokens plus 1,920 long-fixture forced cache steps, short warm-ups, short reference probes and option forwards. Stage 0 generation rates of roughly 9–11 tokens/s suggest several minutes of decode; storage, large prefills, identity hashing, launch overhead and repeated load dominate the uncertainty. Time the first discovery and abort/rebudget if projected wall time exceeds the window. The pilot's separate four-hour/eight-GPU-hour estimate must be revisited with measured option/probe overhead.

Before launch require signed plan/package, independently checked runtime preimages, operator custody checks, exclusive healthy devices, sufficient free memory and enforced containment. Stop on any digest, UUID, class, placement, dtype, input or runtime mismatch; unexpected permission/access; wrong mount inventory; nondeterministic or nonfinite operations; OOM; worker loss; timeouts; incomplete/invalid authenticated pairs; or failed synthetic equivalence/repeatability. During synthetic preflight a load, warm-up, generation, option pass or probe above 42 GiB reserved on either GPU halts the block. This proposed ceiling leaves operating headroom on a 48 GB L40S. The supervisor applies a 900-second handshake limit per load and 180 seconds per item operation. Inspect cap/empty behavior, load and max-envelope VRAM, time-to-first-token, terminal classifications and cost before proposing a live pilot. Operator monitoring enforces the overall allocation and hardware/ECC policy. Preserve failed ledgers. Scientific evaluation still requires separately approved independent items, rights/screening, expert reviewers, the scoring sandbox and the accepted custody process.

For a later authorized pilot, custody provisions per-block plans from the independently signed roster and the single private renderer, with `synthetic=false`, the approved common runtime, and only the four whitelisted job fields. Keep both arm orders counterbalanced as in the accepted protocol; compare matching base/adapter ledgers per block with `audit` (without the synthetic flag), and reconcile all blocks against the external 80-item roster before unlocking scores. This engineering milestone creates no pilot plans or scientific judgments.
