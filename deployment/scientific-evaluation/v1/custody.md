# Custody, blinding and release

The following are service boundaries for a future approved run. A Python field whitelist, an opaque filename and a Git ignore pattern each serve a narrower purpose than access control. The CPU modules exercise the projections and joins; the designated infrastructure operator has to provision and test the actual boundary.

| Principal | May read | May deliver/write |
|---|---|---|
| Independent pilot authors and solvers | Assigned candidate materials, source/licence information, assigned answers | Revision-stamped pilot workpapers to intake. No model outputs before lock |
| Screening and rights officers | Candidate projections, authorized corpus projections, family/rights registries, prior exposure dispositions | Signed private clearance decisions to custodian, with raw flags preserved |
| Independent custody service | Approved current pilot roster, restricted arm/response crosswalks, commitment keys, access logs | Per-role minimum exports, signed locks, later private A/B analysis join |
| Model provisioner and worker supervisor | Pinned models and assigned worker identity, settings, read-only approved input tokens and jobs | Attested private identity/runtime evidence and terminal attempt receipts direct to custody |
| Inference orchestrator | Opaque scheduling tickets and aggregate job state | Dispatch to mediated endpoints only; no filesystem shell on workers, model mounts, arm aliases, private artifact paths, metrics, keys or review packets |
| Objective scorer / code executor | Assigned anonymous response and its frozen rule or suite | Anonymous objective verdict and evidence digest direct to custody. Isolate generated code from host, other jobs and scoring secrets |
| Each expert reviewer | Individually shuffled, single-response tasks, allowed evidence, visible rubric and format | Independent ratings, rationale, fatal-error flag, conflicts and incident reports. No access to the other reviewer's submissions |
| Separate adjudicator | Disputed masked response, evidence, rubric and anonymized reasons after initial lock | Separate adjudication records. No control of original ratings |
| Statistician | Frozen plan, deidentified agreement tables, after unlock the A/B analysis table and permitted metrics | Versioned aggregate analysis and uncertainty; privacy review before release |

A future confirmatory vault belongs to a separate independent authority. It has its own principals, media, access logs and encryption keys, disconnected from the pilot, model operator, assessment services and general search/indexing. This phase creates no such items. The historical seal is a third, excluded trust domain. Prevent recursive indexing, agent access, shell history and logging of private stores. Keep all private mounts outside the checkout, CI workspace, prompt traces and general-purpose telemetry.

1. Provision separate service accounts with deny-by-default ACLs, protected encryption/signing keys, read-only mounts, authenticated one-way exports and an append-only evidence store. No shared UID, inherited environment credentials, all-role database connection or cross-role backup/restore permission. Model paths, process logs, adapter presence, distinctive timings/token counts, decoded outputs and role-bearing queue names can reveal the mapping. Restrict them to the designated principals. The provisioner inevitably knows which artifact it loaded; the orchestration service has no access to the provisioner or its identity evidence. Independent custody privately randomizes the two worker tickets and block order. The public definitions of A and B never specify ticket assignments.
2. Version and sign the source inventories, eligibility and access decisions, locked pilot roster/seed, prompt and score rule commitments, runtime and scoring code, anonymous packet roster and separately the unblinding plan. Commit privately with a secret-key HMAC over canonical bytes or an encrypted immutable manifest. Keep low-entropy prompt/answer hashes out of public logs. Author/reviewer identity crosswalks and key material require separately controlled vault storage. Split custody privileges if the same individual would otherwise author, operate and judge.
3. Test as each real principal using **synthetic canaries** on the actual isolated deployment. Demonstrate authorized reads and denied direct/indirect list, fetch, logs, mounts, caches, metadata endpoints and restores for each forbidden store. Verify no answer-key/arm/future-holdout canary appears in worker, scheduler or reviewer exports. Record signed results and versions. If roles share host-admin access or an operator can inspect model selection, record the failed boundary and hold the blinded run.
4. Use `blind_review.prepare` in custody after checking responses for explicit model self-identification. Preserve raw outputs. Flag any leak as a protocol incident, adjudicate eligibility blind and apply the prespecified paired sensitivity rule. Never silently edit a scientific response to mask a leak. Provide only an authenticated reviewer's own delivery. Group by domain expertise; maintain stable reviewer pairs for agreement within a domain, and separately account for which pair rated each item. Independent reviewers must be conflict-screened and distinct from item authors, model developers and output-aware operators. Save each write-once submission as it arrives with packet commitment, reviewer credential and timestamp. Enforce a submission deadline and access revocation in the private service.
5. `lock_ratings` validates a *complete batch*. For partial review, preserve every actual submission and report missing ratings against the assigned roster. A definitive hard objective failure remains zero. Withhold a positive or human-only score until its required reviews are complete; unrelated completed items may be locked in complete batches. `finalize` checks for two independent ratings per response and a third authenticated adjudication for every ordinal/fatal disagreement. Store the two original ratings, rationale, adjudication, and resulting pass decision separately. Keep unresolved factual disputes null when they determine correctness. Predeclare referral triggers for ambiguous references, conflicting evidence, suspected flawed keys and material safety errors. If either response triggers an item-level referral, send both in individually masked packets to the relevant specialists. Log the referral, preserve objective outcomes and apply the frozen paired invalid-item rule if the key is unusable. Strict format errors retain their specified score. A runner/scorer timeout or an unresolved key never becomes an expert rating.
6. Before breaking the blind, reconcile all outcome tickets and hash the objective records, initial and final ratings, reviewer roster/agreements, exclusions, evidence commitments and analysis code. Sign the freeze and log authorized unblinding. The statistician joins the frozen scores to the mapping in private, with A as base and B as adapted, then runs `analysis.analyze` against the original assignment roster. Record every missing attempt, invalid item, truncation and departure from lock. If access leaks, quarantine the affected unit, log actor/scope, alert the independent custodian and report the potential bias. Changes to the protocol use a new version; keep original observations and their status.
7. Rights and data stewards set retention, revocation, backup access and destruction policy before intake. Maintain a private audit of accesses, signed amendments and deletions. Release only aggregate results after checking sparse cells, personal identifiers, source restrictions and accidental content disclosure.

## Moving records between the CPU components

- `pilot.draw` consumes the private item registry and a previously frozen frame digest. `source_family_id` must bind the connected component across *all* related source IDs from the screening crosswalk, including multi-source cases. Verify `content_commitment` against actual immutable prompt, source, key/rubric/test and clearance bytes before releasing any selected job. Never accept an unsigned self-declaration of clearance.
- Render the question and any evidence/format instructions together through `runner.render_item` once; both workers receive the resulting `Item`. `runner.audit_pairs` reconciles authenticated worker receipts against the pre-run schedule. The private dispatcher makes one anonymous scoring record per delivered response. Preserve `text` exactly as decoded. Only the custodian sees the mapping from response alias to run, slot, item, revision and output commitment.
- Score delivered answers through `score.score` and combine the independently locked rating with `score.final_score`. Invalid keys or malformed receipts are infrastructure incidents. Bind each score lock to both response alias and response hash. The evidence store authenticates identities and enforces immutability; the library accepts verified data in memory.
- `handoff.analysis_row` projects one *audited* receipt and its *locked, response-bound* score after authorized unblinding. Include rows for observed technical failures. For an entirely absent row, first reconcile the assignment ledger with the worker supervisor. If reconciliation cannot be completed, report missingness descriptively and fail the run integrity gate. Keep the frozen roster for `analysis.analyze` even in incident analysis. Use private expert reason codes and claim-level audits alongside the aggregate analysis when required by the item plan.
